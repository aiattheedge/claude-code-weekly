# The wait

Welcome to Claude Code Weekly: Special Edition. Here's a problem I have at my day job. My change is done. The tests pass. Our automated review bot has already commented. And then I wait for a human approval from my engineering team. That review is required, and it should be. But the wait is real, and as agents write more of the code, the queue only gets longer.

# What Anthropic shipped

This week Anthropic launched Claude Ship, three agents for GitHub pull requests, on Team and Enterprise plans. Code Review is generally available. Several agents read each change, a verification step checks the findings, and they're posted inline. It never approves or blocks anything. PR Steward is in beta. It pushes fixes for failing checks, merge conflicts and review comments, and after each push it names the commit to revert. It's designed not to approve or merge. And Claude Approvals, also in beta, is the new one. It's a policy file in your repo that decides who has to approve, and it can let Claude approve routine changes itself.

# The wait isn't the review

Here's the thing. A lot of the wait isn't the review itself. It's the round trips. A reviewer opens the pull request, finds a conflict or a red check, comments, and moves on. You fix it, and you're back in the queue. Code Review and PR Steward go after exactly that. By the time a person looks, the checks are green, the conflicts are merged and the bot's findings are handled. The human review gets shorter, and it happens once.

# Approvals as code

Approvals goes further. The file lives in your repo under dot claude, and Anthropic says it works like a smarter CODEOWNERS file. Billing code can need two people. Test fixtures can need one person once Code Review passes. And you can keep a human on everything. Set Claude to comment, not approve, require one person who isn't the author, and make the Approvals check required in GitHub. The policy is versioned and reviewed like any other code.

# Where I'd keep a human

So where would I let Claude approve? Docs, test fixtures, maybe dependency bumps with green builds. Where would I keep a person? Auth, payments, data migrations, CI workflows, and the policy file itself. Those risk tiers are a leadership decision, not a tool default.

# Read the fine print

A few honest catches. Claude's approval can count as the one approval a GitHub rule asks for. So if a human must sign, say so in the policy. With auto-merge or a merge queue and no person required, a change can merge with nobody acting. Turn on dismissing stale approvals, because GitHub can keep counting an approval after new commits. And it isn't offered yet to companies on zero data retention, HIPAA, or their own encryption keys. That's a lot of regulated companies.

# How I'd start

Here's how I'd start. One repo, in observe mode. Claude posts what the policy would decide and approves nothing. Compare its calls to your reviewers' calls for a few weeks. Then bring that data to whoever owns your review rule. Observe mode still bills, so set spend limits first.
